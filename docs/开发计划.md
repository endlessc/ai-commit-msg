# AI Commit Message — IntelliJ IDEA 插件开发计划

> 目标版本：IntelliJ IDEA 2026.2.3（build 262），本机已安装，可直接作为调试宿主
> 文档状态：v1，待评审
> 参考产品：Qoder 提交面板的「一键生成提交信息」体验（按钮位于提交信息框的工具条上）

---

## 一、要解决的问题

写提交信息是高频、低价值、又容易写烂的动作。Qoder 的做法是：在提交信息框旁边放一个按钮，点一下，读**当前这次提交勾选的文件**，让模型总结成一条符合 Conventional Commits 的提交信息，直接填进输入框。

本插件要做同一件事，且满足三条硬要求：

1. **只分析"这次要提交的"内容**，不是整个工作区。用户在变更树里取消勾选的文件不能出现在生成结果里。
2. **一次点击完成**，不弹窗、不打断，结果可直接编辑、可撤销。
3. **模型服务可换**，OpenAI 兼容协议（DeepSeek / 通义千问 / 智谱 / Kimi / OpenAI / 本地 Ollama 均可），不做厂商锁定。

## 二、非目标（MVP 不做）

- 不做提交、不做暂存、不做任何写 Git 的操作（只读）。
- 不做多轮对话式的提交信息助手。
- 不改动平台提交面板自身的 UI 结构（只往既有工具条里加一个 action）。
- 不做非 Git 的 VCS 深度适配（接口留出来，实现只保证 Git）。
- 不做团队共享配置 / 云端同步。

## 三、交互设计

### 3.1 按钮位置

Qoder 的按钮出现在提交信息框下方那一行：`☐ 修正(M) ｜上次提交▾ ｜历史图标 ｜Qoder 按钮`。

实测这一行就是平台动作组 `ChangesView.CommitToolbar`，其中「修正(M)」是 `Vcs.ToggleAmendCommitMode`，历史图标属于子组 `Vcs.MessageActionGroup`（见 `VcsActions.xml:391-403`）。因此把 action 挂到 `Vcs.MessageActionGroup` 末尾，即可落在历史图标右侧——与 Qoder 位置一致，且不需要任何组件注入。

### 3.2 状态机

| 状态 | 触发 | 界面表现 |
|---|---|---|
| Idle | 默认 | 图标按钮，悬停提示「根据勾选的文件生成提交信息 (⌘⌥G)」 |
| Disabled | 无勾选变更 / 非 Git 仓库 / 未配置模型 | 置灰，悬停提示具体原因 |
| Loading | 点击后 | 提交信息框进入 loading 遮罩（复用平台 `CommitMessage.startLoading()`），按钮变「停止」 |
| Success | 返回并落字 | 写入输入框，右下角轻提示「已生成，⌘Z 可撤销」 |
| Error | 各类失败 | 气泡通知 + 「打开设置」动作；**不覆盖用户已写的内容** |
| Cancelled | 再次点击 | 恢复原状，不写入 |

### 3.3 写入策略

- 输入框为空 → 直接写入。
- 输入框已有内容 → 直接覆盖，但写入走 `Document` 的写命令（保留 undo 栈），并提示可撤销；设置项可改为「先预览」。
- 生成中禁止再次触发，避免并发写同一 Document。

### 3.4 生成结果的形状

对齐 Qoder 截图里的风格：首行 Conventional Commits 标题（含 scope），空行，`- ` 开头的要点列表：

```
feat(hil-script-studio): 初始化项目骨架与工作台基础

- 创建 domain、application、infrastructure、interfaces 分层目录结构
- 新增独立信号包 hil_signals 并完成宿主包模块初始化
- 实现设备回放替身 FakeDeviceBackend，覆盖发现、准备、连接与关闭生命周期
- 装配 Chat 工作台 HTTP API 与 SSE 事件流，支持会话创建、消息收发与任务派发
```

### 5.1 按钮骨架

```kotlin
class GenerateCommitMessageAction : AnAction() {
    override fun getActionUpdateThread() = ActionUpdateThread.BGT

    override fun update(e: AnActionEvent) {
        val ui = e.getData(VcsDataKeys.COMMIT_WORKFLOW_UI)
        val hasContent = ui != null &&
            (ui.includedChanges.isNotEmpty() || ui.includedUnversionedFiles.isNotEmpty())
        e.presentation.isEnabledAndVisible = e.project != null && hasContent
    }

    override fun actionPerformed(e: AnActionEvent) { /* 见第六节 */ }
}
```

`plugin.xml`：

```xml
<actions>
  <action id="AiCommit.Generate"
          class="com.lememo.aicommit.action.GenerateCommitMessageAction"
          icon="AiCommitIcons.Generate"
          text="AI 生成提交信息">
    <add-to-group group-id="Vcs.MessageActionGroup" anchor="last"/>
  </action>
</actions>
```

### 5.2 读取"这次提交的文件"

```kotlin
private fun collectChanges(e: AnActionEvent): List<ChangeItem> {
    val project = e.project ?: return emptyList()
    val ui = e.getData(VcsDataKeys.COMMIT_WORKFLOW_UI)
    if (ui != null) {
        return ui.includedChanges.map { it.toItem(project) } +
               ui.includedUnversionedFiles.map { it.toNewItem() }
    }
    // 兜底：旧模态提交框
    val doc = e.getData(VcsDataKeys.COMMIT_MESSAGE_DOCUMENT) ?: return emptyList()
    val supplier = doc.getUserData(CommitMessage.CHANGES_SUPPLIER_KEY) ?: return emptyList()
    return supplier.get().map { it.toItem(project) }
}
```

### 5.3 写入并保留撤销

```kotlin
val document = e.getData(VcsDataKeys.COMMIT_MESSAGE_DOCUMENT) ?: return
WriteCommandAction.runWriteCommandAction(project, "AI 生成提交信息", null, {
    document.setText(message)
})
```

## 七、数据流

```
点击按钮
  → 取 CommitWorkflowUi 的勾选项（Change[] + 未版本化 FilePath[]）
  → 按仓库根分组，构建 pathspec
  → git diff HEAD -- <paths>（+ 未跟踪文件按新增处理）
  → DiffFilter 剔除二进制/锁文件/生成物
  → DiffTrimmer 按预算裁剪，保留 stat 全量
  → PromptBuilder 组装 messages（system + user）
  → OpenAiCompatibleClient 调 /chat/completions（后台线程，可取消）
  → MessagePostProcessor 规整
  → WriteCommandAction 写入 Document
  → 气泡提示（成功可撤销 / 失败原因 + 去配置）
```

## 八、Diff 采集与裁剪

### 8.1 为什么用 git CLI 而不是平台 `ContentRevision`

平台侧重算 diff 需要 `ContentRevision` + `UnifiedDiffWriter`，要自己处理新增/删除/重命名/编码/大文件，代码量翻几倍且容易在边界上出错。`git diff HEAD -- <paths>` 一次拿到与"提交后"等价的结果（提交写入的是工作区内容），重命名、换行符、二进制识别都由 Git 处理。代价是依赖 `git` 可执行文件——IDE 用户必然具备，缺失时给出明确报错即可。

### 8.2 采集细节

- 仓库根：`git -C <file.parent> rev-parse --show-toplevel`，按根分组（天然支持多仓库/多根项目）。
- 已跟踪：`git diff HEAD --no-color --no-ext-diff -U3 -- <paths>`。
- 未跟踪：`git diff HEAD` 不含，需读文件内容按「整文件新增」拼 `+` 行，超过 400 行截断。
- 删除文件：diff 自带，无需特殊处理。
- 文件数 > 200：只对前 100 个文件取 diff，其余仅进 stat，并在 prompt 里注明。
- 单次采集耗时目标 < 500ms；超时 5s 放弃 diff、退化为「仅文件清单」。

### 8.3 过滤清单（不计入 diff，但仍出现在文件清单）

| 类别 | 规则 |
|---|---|
| 二进制 | `git diff --numstat` 中为 `-/-`，或扩展名命中图片/字体/音视频/压缩包 |
| 锁文件 | `package-lock.json`、`pnpm-lock.yaml`、`yarn.lock`、`poetry.lock`、`Cargo.lock`、`go.sum`、`Gemfile.lock`、`composer.lock` |
| 生成物 | `build/`、`dist/`、`out/`、`target/`、`node_modules/`、`vendor/`、`*.min.js`、`*.map`、`*.pb.go`、`*_generated.*` |
| IDE 元数据 | `.idea/`、`*.iml`（可在设置里开关，默认忽略） |

### 8.4 预算与裁剪

- 默认 `maxDiffChars = 40_000`（约 15k token），可调。
- stat 全量先占位（最多 200 行）。
- diff 片段排序：源码 > 配置 > 文档 > 测试；同级别按 diff 行数**升序**（小改动信息密度高，先保证每个文件都能露一次面）。
- 单文件上限 400 行 / 8k 字符，超出保留前若干 hunk 并标注 `… (省略 N 行)`。
- 触顶后停止追加，末尾写 `（另有 N 个文件未展开：a.kt, b.ts …）`。

## 九、Prompt 设计

**system**（内置，可被用户模板覆盖）：

```
你是一名资深工程师，负责为 Git 变更生成规范、准确的提交信息。
必须遵守：
1. 只输出提交信息本身，不要解释、不要前言、不要代码块包裹。
2. 首行格式 <type>(<scope>): <subject>，type 取 feat|fix|refactor|perf|test|docs|build|ci|chore|style|revert，
   subject 用中文、动词开头、不超过 50 字、不加句号；scope 从模块或目录名推断，无法确定时省略括号。
3. 空一行后，用 "- " 列出 3–8 条要点，每条说明行为变化，不要逐个罗列文件，不要把纯格式化改动写成要点。
4. 代码标识符、专有名词保留原文；其余用中文。
5. 不要编造代码里没有体现的功能。
```

**user** 模板变量：

| 变量 | 内容 |
|---|---|
| `{{repo}}` `{{branch}}` | 仓库名、当前分支（`git rev-parse --abbrev-ref HEAD`） |
| `{{stat}}` | `git diff --stat` 输出 |
| `{{diff}}` | 裁剪后的 unified diff |
| `{{recent_subjects}}` | 最近 30 条提交标题，用于模仿本仓库的措辞习惯 |
| `{{language}}` `{{style}}` | zh/en、conventional/plain |

`{{recent_subjects}}` 是低成本高收益项：同一个仓库历史里常有固定的 scope 命名与动词习惯，给模型看 30 条标题能显著提升"像本仓库写的"的感觉。

## 十、模型接入

- 协议：OpenAI 兼容 `POST {baseUrl}/chat/completions`；`baseUrl` 允许带或不带 `/v1`，客户端做归一化。
- 预设：DeepSeek（`https://api.deepseek.com`）、通义千问（DashScope compatible-mode）、智谱 GLM、Kimi、OpenAI、Ollama（`http://localhost:11434/v1`）、自定义。
- 请求：`temperature=0.2`、`max_tokens=1024`（推理型模型如 deepseek-flash 容易被思考链吃满预算，设置里可调到 8192，并在响应 `finish_reason == "length"` 时明确报「输出预算不足」，不静默返回半截）。
- 超时：连接 10s、读取 120s；`ProgressIndicator` 取消时中断请求。
- 无流式（M1）→ SSE 流式（M3）：流式需要 `java.net.http.HttpClient` 逐行读 `data:`，届时保留"非流式"作为兜底开关。
- 隐私：请求只发 diff 文本，不发整仓；README 明示；本地 Ollama 可完全离线。

## 十一、配置与密钥

应用级配置（一次配置，全项目生效），`AiCommitSettings : PersistentStateComponent<State>`：

| 分组 | 项 | 默认值 |
|---|---|---|
| 服务 | 预设、Base URL、模型名、API Key | 空，未配置则按钮置灰并提示去配置 |
| 生成 | 语言（中文/English/跟随 IDE）、格式（Conventional/纯文本/自定义模板）、生成后行为（覆盖/仅空时填/先预览） | 中文、Conventional、覆盖 |
| 高级 | maxDiffChars、单文件行数上限、超时、max_tokens、temperature、忽略 `.idea`、自定义 system prompt | 见第八、十节 |
| 操作 | 「测试连接」「拉取模型列表」（`GET /models`） | — |

API Key 走 `CredentialStore`（`CredentialAttributes("com.lememo.aicommit", modelHost)`），配置文件里只存是否存在。

## 十二、线程与生命周期

- `AnAction.getActionUpdateThread() = BGT`，`update()` 里只读轻量状态，不触发 Git 调用。
- 采集 + 请求在 `Task.Backgroundable`（带取消）中执行；所有 Document 写入回到 EDT 并用 `WriteCommandAction`。
- 一个项目同时只允许一个生成任务；任务挂在 `project` 上，项目关闭自动取消。
- 不缓存 diff（勾选状态随时会变），但缓存"仓库根 → 是否 Git 仓库"判定。

## 十三、失败与降级矩阵

| 情况 | 行为 |
|---|---|
| 无勾选变更 | 按钮置灰，提示「请先勾选要提交的文件」 |
| 非 Git 仓库 | 按钮置灰，提示「当前项目不是 Git 仓库」 |
| 未配置模型 | 点击后弹出配置引导，不发起请求 |
| git 不可用 / 超时 | 退化为仅文件清单 + stat，正文注明「(未获取到 diff)」 |
| HTTP 401 | 「API Key 无效或已过期」+ 去配置 |
| HTTP 404 | 「Base URL 或模型名不正确」+ 去配置 |
| HTTP 429 | 「请求过于频繁或额度不足」 |
| 超时 / 网络错误 | 「请求超时（可调大超时或减小 diff 预算）」，保留原文 |
| 响应为空或 `finish_reason=length` | 「模型未返回有效内容，请检查 max_tokens」 |
| 用户取消 | 静默恢复，不写 Document |

## 十四、里程碑与验收

### M0 骨架（0.5 天）

产出：`git init` + Gradle 工程 + `plugin.xml` + 空 action + 图标 + `.gitignore`。
验收：`./gradlew runIde` 起沙箱 IDE，打开任一 Git 仓库，提交面板出现 AI 按钮，位置在历史图标右侧；点击弹「未实现」通知；控制台无异常。
同时验证两个不确定点：`localPath` 依赖写法、Gradle 版本与插件 2.20.1 的兼容性。

### M1 主链路可用（1 天）

产出：采集 → git diff → 过滤裁剪 → 调模型 → 写入 → loading/取消。
验收清单：

1. 只勾选 2 个文件时，生成内容不涉及第 3 个未勾选文件。
2. 未跟踪的新文件能被分析，且描述里体现「新增」。
3. 勾选内容全是二进制时给出提示，不写入空信息。
4. 点击后信息框出现 loading，再点可取消，取消后原文不变。
5. 生成结果在输入框内可 `⌘Z` 一键撤销。
6. API Key 错误时气泡提示，且不覆盖原有文本。

### M2 可配置（1 天）

产出：设置页全量项、测试连接、模型列表、`recent_subjects` 风格few-shot、快捷键。
验收：换 DeepSeek / Ollama 两个服务各生成一次成功；设置页改语言为 English 后产出英文提交信息；测试连接对错误 Key 给出 401 文案。

## 十六、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| `CommitWorkflowUi`、`CommitMessage` 属平台内部实现包，未来版本可能改签名 | 升级 IDEA 后按钮失效 | 兼容旧路径的兜底分支；`until-build` 留空但在 M4 加启动自检，异常时降级为「仅文件清单」并提示；升级到 263 时先跑一次冒烟 |
| `Vcs.MessageActionGroup` 在 262 之外位置不同 | 按钮跑到别处 | 已确认 262 的组定义；M0 即肉眼验收位置 |
| Gradle 9 / 2.20.1 不兼容 | 构建失败 | 固定 wrapper 8.14.x；失败再降 2.7.0 + Gradle 8.13 |
| `localPath` DSL 形式与文档不符 | 无法用本地 IDE | 回退 `intellijIdea("2026.2.3")` 走官方安装包 |
| 大 diff 超上下文 | 生成失败或质量差 | 双层预算（总字符 + 单文件），stat 优先，触顶显式标注 |
| 代码外发顾虑 | 用户不敢用 | 默认不自动生成；README 声明数据流向；支持纯本地 Ollama |
| 生成内容与实际改动不符 | 提交信息失真 | prompt 禁止编造 + 不带未勾选文件 + `recent_subjects` 对齐仓库风格 |

## 十七、发布与安装

## 十九、实施记录（2026-11-18）

计划中的若干假设在实际构建时被推翻，记录在此，避免重复踩坑：

| 计划假设 | 实际情况 | 处理 |
|---|---|---|
| Gradle wrapper 8.14 | IntelliJ Platform Gradle Plugin 2.20.1 **要求 Gradle 9.0+** | 改用本机已装的 9.2.1 |
| Kotlin 2.2.20 | 平台 262 的类使用 **Kotlin 2.4 元数据**，2.2 读不了，报一堆假的 Unresolved reference | 升到 2.4.21 |
| `localPath(...)` 指定本地 IDE | 2.20.1 里没有这个方法 | 正确写法是 `local(path)` |
| 可用 `CommitMessage` 做模态提交框兜底 | 该类在 `intellij.platform.vcs.impl.jar`，**impl jar 不在编译类路径**（平台只暴露 API 模块） | 去掉兜底，只走 `CommitWorkflowUi` |
| `CommitWorkflowUi.includedChanges` | 该接口是 Kotlin，`getIncludedChanges()` 是**函数**不是属性 | 改函数调用 |
| `PasswordSafe.getInstance()` | 2026.2 里被 Kotlin 隐藏 | 用 `PasswordSafe.instance` |
| 用平台 Test Framework 跑测试 | 其 JUnit5 监听器需要 IDE 进程，纯逻辑测试起不来 | 去掉 testFramework，改纯 JUnit5 |
| `HttpRequests.post(url, body)` 会发出 JSON 请求体 | **不会**。262 上实测只发请求头，body 为空；服务端（硅基流动）返回 400 `code=20015 参数无效`，表现为「配置明明正确却一直报错」 | 改为 `post(url, "")` + 在 `connect {}` 里 `request.write(payload)`，并补了本地回环回归测试 |

其余落点与计划一致：按钮挂在 `Vcs.MessageActionGroup`；`VcsDataKeys.COMMIT_MESSAGE_CONTROL` 在该上下文可用（平台自带的
`ShowMessageHistoryAction` 就是这么取的）；`VcsDataKeys.COMMIT_MESSAGE_DOCUMENT` 用于写入并保留 undo。

已用 `buildSearchableOptions` 在无头 IDE 中加载插件并实例化设置页，说明 plugin.xml、扩展点与 Configurable 均有效。
